# Native-discovered shortfall cap correction

The release coordinator observed this on replacement APK 0.0.3 on the Galaxy S9, dated 28 September: £1,800 current cash already including salary, monthly payday 28, £950 rent/bills occurrence due 12 September still unpaid and another due 12 October, £70/week essentials, £200 buffer, no active debt. Today correctly showed £0 available and a £600 shortfall. Opening the shortfall card incorrectly showed a £400 gap and recommended £33/day for 30 days.

Root cause: `ShortfallScreen.tsx` used the raw cash chart minimum for its gap, omitting the protected buffer, and based its daily spending allowance on `route.spare`, which is closing cash **on the next payday including that future salary**. The exact source reproduction is £1,390 payday closing cash, £400 raw cash deficit, and `floor((1390 - 400) / 30) = £33/day`. This was a consumer of the old route semantics; the canonical financial plan itself returned the correct minus £600 headroom.

Correction: the pure `shortfallBudget.ts` selector derives the gap and discretionary allowance from the route's canonical `safeToSpend`. Whole-pound gaps round upward, daily allowances downward. `ShortfallScreen.tsx` consumes this selector for its verdict, borrow amount and spending card. The card says **extra spending**, preserves essentials in the plan, and explicitly explains that spending £0 extra does not close the unresolved gap. Existing navigation, pause, pot and What-if actions remain in place.

Deterministic evidence in `shortfall-cap-before.txt`: the extracted unchanged legacy calculation failed 5 of 6 regression tests. The exact native inputs returned **£400 gap / £33 daily cap**. After the correction, `shortfall-cap-after.txt` records all **50 focused tests passing**, including seven new selector/store regressions and existing payday, overdue obligation, recovery and day-clock tests. The same inputs now return **£600 gap / £0 daily discretionary cap**. Marking only September rent explicitly paid leaves October protected: **£350 safe / £11/day**, with no active shortfall. Raising the future salary to £5,000 cannot increase present discretionary capacity. Tests also cover a buffer-only deficit, fractional rounding and an unready route. Mobile TypeScript validation passes.

The touched Shortfall screen now uses the existing `useDayClock`, refreshing at local midnight and app foreground without a remount. Existing hook tests cover both transitions and disposal. The card still navigates to the independent What-if preview; it does not apply a cap or pass an amount. That preview uses the canonical budget: the default £40 scenario leaves minus £640; a £0 scenario leaves minus £600. An explicit What-if £0 hold is rejected as a no-op by its existing store API. A separate invariant test calls the existing `setSpendHold(0, 30)` API and its clear operation: the zero discretionary hold retains the £300 essential allowance, both rent occurrences, all cash/debt/ledger state and the minus £600 protected gap. No global hold semantics were changed.

The release coordinator separately confirmed on S9 APK 0.0.3 that marking September rent paid returns Today's £350 safe and undoing that confirmation restores £0 available / £600 shortfall. The new Shortfall screen correction still requires the coordinator's next signed APK and native verification; source test results are not presented as device results.
