# Open Banking (AIS) Provider Decision — Folio/Melo

Status: research complete, no build started. Owner sign-off required before any provider account is created (see §4).
Scope: read-only Account Information Services (AIS) only. No payments (PIS). UK-only.

## 1. TL;DR + Recommendation

**Recommend TrueLayer as the primary target, with Tink as the named runner-up.** Neither offers self-serve production pricing — every credible UK AIS provider for a solo pre-revenue app gates real pricing behind a sales call in July 2026 — so this is a "best available path," not a clean win. TrueLayer edges out Tink on two concrete points: its sandbox-to-production pipeline is a single Console (no separate domain/migration step) and its agent-of-TrueLayer licensing path is described as available without a pre-existing paid contract, whereas Tink explicitly gates full white-label Link behind "licensed customers" and Plaid gates its agent path behind its own Scale plan. GoCardless (ex-Nordigen) is disqualified outright — new signups have been closed since ~Aug 2025 with no reopening date, confirmed on their own status page. Plaid is viable but structurally slower for a UK solo founder (separate UK/EU production-access ticket, ~90-day go-live review, no first-party Expo path).

**Switch trigger:** if TrueLayer's sales conversation returns either (a) no viable agent-registration path without first signing a paid Scale contract, or (b) a quoted AIS cost that breaks the 1,000-user ceiling in §3, re-run the same sales conversation with Tink before falling back to Plaid. Do not default to Plaid on TrueLayer failure — Plaid's production-access gate is slower, not faster, and its agent path has the same paid-tier gate as Tink.

Every number in the table below is either directly sourced or explicitly marked unverified — no figure here should be used to set a budget until confirmed by a live sales call.

## 3. Integration Plan Mapped to This App

### Architecture fit

This app already runs the exact shape needed: a thin Cloudflare Worker proxy (`services/ai-gateway`, deployed as `folio-ai-gateway`) that holds a provider secret server-side and the RN app never sees it — see `services/ai-gateway/src/index.ts`, which already does this for the OpenRouter key (`OPENROUTER_API_KEY` as a Wrangler secret, `x-folio-gateway-token` as a weak abuse guard). The AIS integration reuses this exact pattern with a second secret (the AIS provider's client_secret) instead of standing up new infrastructure.

The existing statement-reader flow (`apps/mobile/src/folio/screens/IntakeScreen.tsx`, `src/local/statementReaderClient.ts`) already proves the "gateway does the provider call, app gets back normalized `CandidateMoneyItem[]`, user lands in Review" pattern end-to-end for PDF/photo extraction. AIS should be built as a sibling reader, not a new subsystem: same destination (`ReviewScreen.tsx` via `reviewDedupe.ts`), different source.

### Phases

**Phase 0 — Provider account + compliance gate (owner action, not engineering).** Owner signs up for the chosen provider's Console (self-serve, same-day) and separately opens the production/sales conversation (see §4). This phase blocks nothing else — Phase 1 can start same-day against sandbox.
Effort: 0 engineering days. Timeline: sandbox access same-day; production approval unbounded until a sales call happens (est. 2–6 weeks based on comparable providers' documented processes).

**Phase 1 — Worker: auth-link + token exchange endpoints (new routes on `folio-ai-gateway`).** Add two routes to the existing Worker: `POST /bank/auth-link` (calls the provider's "generate auth link" endpoint, returns the redirect URL to the app) and `POST /bank/callback` (receives the provider's auth code server-side, exchanges for access/refresh tokens, stores them — needs a small KV or D1-backed token store keyed by a local device/user id, since the Worker is currently stateless). This is the only genuinely new backend surface; everything else reuses the existing Worker shell (CORS, token-guard, JSON helpers already in `index.ts`).
Effort: 2–4 days (mostly the token-storage decision — Cloudflare KV is the lightweight fit given the Worker has no DB today).

**Phase 2 — RN: web-redirect account-linking screen.** New screen (sibling to `IntakeScreen.tsx`) that calls the Worker's `/bank/auth-link`, opens the result in `expo-web-browser`'s `openAuthSessionAsync` (not a bare WebView — TrueLayer and most providers document that banks block iframe embedding), and handles the deep-link return. On success, the Worker has tokens; the app holds nothing but a "linked" flag.
Effort: 3–5 days, mostly redirect/deep-link edge cases (Android app-to-app bank redirects, user-cancels-mid-flow, expired-consent re-link).

**Phase 3 — Worker: transaction-pull + normalization endpoint.** `POST /bank/transactions` on the Worker — pulls from the provider's Data API using the stored token, normalizes to the same `CandidateMoneyItem[]` shape the statement reader already produces, returns to the app.
Effort: 3–5 days, largely mapping provider transaction fields (merchant, amount, date, category if present) onto the existing candidate shape so `reviewDedupe.ts` needs zero changes.

**Phase 4 — RN: wire into intake → dedupe → Review.** The candidates from Phase 3 feed straight into the existing `setReaderCandidates` → Review pipeline, exactly like a PDF read today. This should be near-zero new code in `ReviewScreen.tsx`/`reviewDedupe.ts` if Phase 3's normalization is done right — the whole point of reusing the existing pattern.
Effort: 1–2 days, plus dedupe testing against real bank data shapes (recurring transactions, pending vs settled, refunds) which the CSV/statement path may not have exercised the same way.

**Phase 5 — Re-link / consent-expiry handling.** AIS consents expire (typically 90 days under PSD2 SCA rules) and need a re-auth flow reusing Phase 2's screen. This is new behavior the statement-reader flow never needed (a PDF doesn't expire).
Effort: 2–3 days.

**Total engineering estimate: ~11–19 days**, excluding Phase 0's unbounded compliance-approval wait, which should run in parallel with Phases 1–2 (build against sandbox while production access is negotiated).

### Cost curve (0 / 100 / 1,000 users)

All figures below are **unverified sales-gated estimates**, not commitments — treat as planning inputs only until a real quote lands.

- **0 users (sandbox/dev):** £0. Every provider's sandbox is free with no time limit.
- **100 users:** Using the one concrete (if unverified) TrueLayer signal — a per-bank-tier platform fee (£1,750–5,000, period unstated) — cost at 100 users could range from effectively fixed-platform-fee (if that figure is monthly-flat) to low-hundreds-of-pounds/month (if it's a per-connection annual figure and most users hit 1–2 banks each). Tink's unverified €0.50/user/month would put 100 users at ~€50/month, structurally cheaper _if_ it holds at this scale — but Tink's real gate is the licensing/contract requirement, not the per-user rate. **Do not commit to a provider based on this figure — get a real quote before 100 real users are onboarded.**
- **1,000 users:** This is the scale where "sales-gated" pricing actually starts to matter and where a per-user model (Tink's reported shape) vs. a platform-tier model (TrueLayer's reported shape) diverges most — a flat £5,000/month all-accounts tier is cheap at 1,000 users (£5/user), whereas €0.50/user/month scales linearly (~€500/month, cheaper in this specific comparison). This crossover is exactly why both quotes should be requested side by side rather than picking on sandbox friction alone.

## 4. Decision Gates — what must be true before build starts

1. **Provider sales call completed with a real quote in hand.** Phase 1 (Worker routes) can be built against sandbox without this, but no production token should ever be exchanged for a real user's bank data until the owner has seen and accepted an actual price — not the unverified figures in §2/§3.
2. **Licensing path confirmed, not assumed.** The owner (not engineering) must get a direct answer from the provider on whether Folio/Melo can operate as an unregistered agent under the provider's FCA license, and under what conditions (insurance, contract tier, compliance review). This is a real regulatory question, not a formality — do not proceed to real bank data on the assumption that the "agent model" quietly applies.
3. **Privacy copy + consent flow rewritten before this ships — flagged explicitly, this is not optional.** `apps/mobile/src/surfaces/pressureMap/trustControl.tsx` currently states, verbatim and prominently: _"No cloud, no account"_ and _"It stays on this device"_ (see lines 56–58, `GUARANTEES` array), with an in-code comment explicitly noting these claims are "kept honest" because they are "both true here." **Connecting a real bank account makes both of these false** — bank data will pass through TrueLayer/Tink's servers and through the Folio Worker (holding tokens), and a live OAuth consent screen is definitionally "an account" in the sense a user will read it. This is a direct, load-bearing contradiction between existing shipped copy and the AIS feature, not a nice-to-have polish item. Before Phase 2 ships to any real user: (a) `trustControl.tsx`'s guarantee copy must be rewritten to describe what's actually true post-AIS (e.g., distinguish "manual/statement entry stays local" from "bank-linked accounts route through your bank + our provider + this app's proxy"), (b) a real consent screen must appear at the point of linking a bank (not buried in settings) naming the AIS provider and what data leaves the device, (c) the "Start fresh" / data-export promises in the same screen need to be checked against whether they still hold for bank-linked data sitting server-side in the Worker's token store. This is a copy/product decision for the owner, not something engineering should silently reinterpret — surface it as an explicit sign-off item.
4. **Cost ceiling set by the owner.** Given every provider's real price is unknown, the owner should set an explicit "walk away above £X/month at Y users" number before the sales call, so the sales conversation has a decision rule instead of becoming an open-ended negotiation.
5. **Token-storage decision made (Cloudflare KV vs. D1 vs. other) for the Worker.** The Worker is currently fully stateless (`services/ai-gateway/src/index.ts` has no storage binding at all); Phase 1 requires picking and provisioning a store before any code is written.

## 5. Open Questions

- Does TrueLayer's agent-registration path actually apply without a paid Scale-tier contract, or does it have the same gate Plaid's FAQ discloses? Not confirmed in this research pass — needs a direct sales question.
- What is TrueLayer's actual production-approval timeline? Unpublished; Tink and Plaid have the same gap except Plaid's is bounded by a documented (if slow) ~90-day process.
- Is the £1,750/£3,250/£5,000 TrueLayer figure monthly or one-off, and does it bundle unlimited calls or cap them? Unknown — the source page shows the numbers with no billing-period label.
- Can Monzo/Starling/Revolut coverage on Plaid be confirmed via `/institutions/get` with `country_codes:['GB']`? Not done in this pass; only relevant if TrueLayer and Tink both fall through.
- What exactly counts as "the app becomes a regulated entity" vs. "agent of a regulated entity" from the FCA's perspective once Folio actually stores a refresh token server-side (in the Worker) rather than merely displaying data? This sits at the boundary of AIS agent rules and hasn't been directly addressed by any source in this research — worth a specific question to whichever provider's compliance team is engaged.
- Does GoCardless's signup freeze (`bankaccountdata.gocardless.com/new-signups-disabled`) show any sign of lifting? Worth a re-check immediately before Phase 0, since it was the cheapest historically-reported option and a reopening would change the recommendation.
- Should Enable Banking be researched as a fifth option? It was flagged by the Actual Budget community as "the only free option" after GoCardless's freeze, but was not researched in this pass — worth one more research cycle if TrueLayer's sales call comes back unfavorable.
